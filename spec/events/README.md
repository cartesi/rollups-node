# TLA+ Specification: Hybrid Event System

Formal specification and trace validation for the rollups-node hybrid event
system. The event system coordinates services using PostgreSQL `LISTEN`/`NOTIFY`
as an advisory fast path, with periodic database polling as a liveness safety
net.

## Overview

The specification models a system with:

- A **database** (source of truth) containing work items with statuses
  (`ABSENT` -> `PENDING` -> `DONE`).
- An **unreliable event channel** (fire-and-forget notifications that may be
  dropped at any point).
- **Workers** that wake up either from events (fast path) or periodic sync
  timers (safety net).

The key design invariant: **events affect only WHEN database state is observed,
never WHAT is observed.** The database is always the source of truth.

## The Model

### Variables

| Variable | Type | Maps to in Go |
|----------|------|---------------|
| `db` | `[1..MaxItems -> {"ABSENT", "PENDING", "DONE"}]` | PostgreSQL rows with status columns |
| `eventChannel` | `SUBSET 1..MaxItems` | In-flight notifications in `memory.Bus` or PG `NOTIFY` |
| `workerState` | `[Workers -> {"idle", "processing", "dead"}]` | Service lifecycle state |
| `workerClock` | `[Workers -> 0..SyncInterval]` | Steps since last poll timer tick |
| `processed` | `SUBSET 1..MaxItems` | Cumulative set of processed items (for verification) |
| `producerNext` | `1..(MaxItems+1)` | Next item ID to produce |

### Actions

| TLA+ Action | Go Implementation | Description |
|-------------|-------------------|-------------|
| `ProduceItem` | `Publisher.Publish()` after DB write | Write item to DB as PENDING; non-deterministically deliver or drop the notification |
| `EventWakeup(w)` | `<-s.EventChannel` in `Serve()` | Worker receives event, queries ALL pending items, marks them DONE |
| `SyncWakeup(w)` | `<-s.Ticker.C` in `Serve()` | Poll timer fires, queries ALL pending items, marks them DONE |
| `RescheduleWakeup(w)` | `<-s.rescheduleChan()` in `Serve()` | Self-continuation: worker found remaining work during previous Tick(), queries ALL pending items |
| `ClockTick` | `time.Ticker` internal | Advance sync timer for an idle worker |
| `WorkerCrash(w)` | Context cancellation / process death | Worker dies, loses in-memory state and LISTEN connection |
| `WorkerRestart(w)` | Service framework restart | Dead worker comes back online; sync timer fires immediately |

Both `EventWakeup` and `SyncWakeup` call the same `Tick()` method, which
re-queries the database for ALL pending work. This is why events carry no
authoritative data — they are pure wake-up signals.

### Properties

**Safety (checked as invariants):**

- `Safety_TypeOK` — All variables are in their correct domains.
- `Safety_NoDuplicateProcessing` — An item marked DONE in the database was
  actually processed: `db[i] = "DONE" => i in processed`.

**Safety (checked as action properties — `[][...]_vars`):**

- `Safety_LifecycleMonotonic` — Item lifecycle is monotonic: items transition
  `ABSENT -> PENDING -> DONE` and never go backward. Holds by construction
  but stated explicitly as a regression check.
- `Safety_ProcessedMonotonic` — The `processed` set only grows (items are
  added, never removed).

**Liveness (checked as temporal property):**

- `Liveness_EventualProcessing` — Every item that becomes PENDING is eventually
  processed to DONE: `(db[i] = "PENDING") ~> (db[i] = "DONE")`. Holds under
  strong fairness of `SyncWakeup` (the poll timer eventually fires even if the
  worker crashes and restarts repeatedly).

### Fairness

The specification uses **strong fairness** (`SF`) for `SyncWakeup` and
`EventWakeup`, and **weak fairness** (`WF`) for `RescheduleWakeup`,
`WorkerRestart`, and `ClockTick`.

**Liveness boundary condition:** `Liveness_EventualProcessing` and the drain
protocol's `Liveness_DrainCompletes` both depend on `WF(WorkerRestart)` — dead
workers eventually restart. If this assumption is violated (e.g., Kubernetes
restart backoff limit reached, or the service is permanently OOM-killed), the
liveness properties do not hold. In production, this means the service
framework (Kubernetes, Docker restart policy) must be configured to always
restart failed services. Strong fairness is required for event and
sync wakeups because workers can crash when an action is enabled, disabling it
temporarily — weak fairness would not guarantee eventual execution in that
scenario. `RescheduleWakeup` uses WF because its enabling condition (pending
work + idle worker) persists until acted upon — no external interference can
disable it transiently.

## Running the Model Checker

### Prerequisites

Download `tla2tools.jar` from
[the TLA+ releases page](https://github.com/tlaplus/tlaplus/releases).

### Full Model Checking

Exhaustively explores all reachable states (1,764 distinct states with default parameters)
and verifies both safety invariants and the liveness property:

```bash
cd spec/events/
java -jar tla2tools.jar \
  -config HybridEvents.cfg \
  -workers auto \
  -metadir /tmp/tlc \
  MC.tla
```

Expected output: `Model checking completed. No error has been found.`

### Adjusting Parameters

Edit `MC.tla` to change the state space:

```tla
MC_MaxItems == 3        \* Number of work items (increase = exponential state growth)
MC_Workers == {"w1", "w2"}  \* Worker set
MC_SyncInterval == 2    \* Poll timer interval in abstract steps
```

## Trace Validation

Trace validation checks that execution traces from the Go implementation
conform to the TLA+ specification. It bridges the gap between the abstract
formal model and the concrete code.

### How It Works

```
 Go Test (trace_test.go)              TLA+ (TraceHybridEvents.tla)
 ========================              ============================

 1. Initialize TLA+ state             TraceInit:
    (db, eventChannel, workers...)       Set variables = trace[1]

 2. Loop: choose random action         TraceNext:
    from enabled actions                  step' = step + 1
    (ProduceItem, EventWakeup,            vars' = trace[step + 1]
     SyncWakeup, ClockTick,               AND some action from
     WorkerCrash, WorkerRestart)          HybridEvents.Next holds

 3. Execute action using REAL           TLC checks:
    memory.Bus + Coalesce()              - Does a valid action exist
    for event delivery                     that produces this transition?
                                         - Do safety invariants hold?
 4. Record full state snapshot
    after each action

 5. Generate Trace.tla module           If TLC finds deadlock before
    with state sequence                  trace end: the implementation
                                         deviated from the spec.
 6. Run TLC on TraceHybridEvents
```

The simulation is **deterministic** given a seed (using `math/rand/v2.PCG`),
so traces are reproducible. Multiple seeds are tested for coverage of
different action interleavings.

The event delivery during the simulation uses the **real** `memory.Bus` and
`events.Coalesce()` — not mocks. This validates that the actual event
infrastructure produces behaviors consistent with the TLA+ model.

### What Gets Validated

For each state transition in the trace, TLC checks:

1. **Action consistency** — There exists at least one action from
   `HybridEvents.Next` (ProduceItem, EventWakeup, SyncWakeup, ClockTick,
   WorkerCrash, or WorkerRestart) whose preconditions hold in the pre-state
   AND whose effects produce the observed post-state. If no action matches,
   TLC reports deadlock — meaning the Go code produced a state transition
   that the formal model cannot explain.

2. **Safety invariants** — At every state in the trace:
   - `Safety_TypeOK`: all variables are in valid domains.
   - `Safety_NoDuplicateProcessing`: no item is marked DONE without having
     been processed.

The Go test also checks these invariants independently (without TLC), so
safety verification works even when `tla2tools.jar` is not installed.

### Running Trace Validation

**Via Go test (recommended):**

```bash
# Safety checks only (no TLC required):
go test ./internal/events/trace/

# With TLC validation:
TLA_TOOLS_JAR=/path/to/tla2tools.jar go test -v ./internal/events/trace/

# Via Makefile:
make unit-test TEST_PACKAGES=internal/events/trace
TLA_TOOLS_JAR=/path/to/tla2tools.jar make unit-test TEST_PACKAGES=internal/events/trace
```

The test automatically finds `tla2tools.jar` from:
1. `TLA_TOOLS_JAR` environment variable
2. `/opt/tla/tla2tools.jar`
3. `~/tla2tools.jar`

If not found, TLC validation is skipped (Go-side safety checks still run).

**Manual TLC run (for debugging):**

The Go test generates a `Trace.tla` file in a temp directory and prints
instructions for running TLC manually. Run with `-v` to see the path:

```bash
go test -v ./internal/events/trace/ -run TestTraceGeneration/seed_42
# Output includes: "To run TLC manually: cd /tmp/... && java -jar ..."
```

Then:

```bash
cd /path/to/temp/dir
java -jar tla2tools.jar \
  -config TraceHybridEvents.cfg \
  -deadlock \
  -workers auto \
  TraceHybridEvents
```

The `-deadlock` flag is required because the trace is finite — TLC would
otherwise report deadlock when the trace ends (no more `TraceNext` steps
are enabled).

### Generated Trace Format

The Go test generates a `Trace.tla` module containing the recorded state
sequence. Each entry is a TLA+ record with all model variables:

```tla
trace == <<
  [ action |-> "Init",
    db |-> (1 :> "ABSENT" @@ 2 :> "ABSENT" @@ 3 :> "ABSENT"),
    eventChannel |-> {},
    workerState |-> ("w1" :> "idle" @@ "w2" :> "idle"),
    workerClock |-> ("w1" :> 0 @@ "w2" :> 0),
    processed |-> {},
    producerNext |-> 1 ],
  [ action |-> "ProduceItem",
    db |-> (1 :> "PENDING" @@ 2 :> "ABSENT" @@ 3 :> "ABSENT"),
    eventChannel |-> {1},
    workerState |-> ("w1" :> "idle" @@ "w2" :> "idle"),
    workerClock |-> ("w1" :> 0 @@ "w2" :> 0),
    processed |-> {},
    producerNext |-> 2 ],
  ...
>>
```

Functions use TLC's `:>` (singleton function) and `@@` (function merge)
operators. Sets use standard TLA+ `{1, 2, 3}` notation.

## Known Limitations

### Non-Atomic Processing (Spec vs. Implementation Gap)

The TLA+ spec models `EventWakeup(w)` and `SyncWakeup(w)` as **atomic**: they
read all pending items, mark them DONE, and clear the event channel in a single
step. In the real Go implementation, `Serve()` receives a coalesced signal,
calls `Tick()`, which executes a database query, processes results (which can
take seconds for machine advance operations), and writes back. During this
window, new events can arrive and be coalesced into a new signal.

**What this means in practice:**

- The spec cannot model events arriving *during* processing. In the real system,
  a `ProduceItem` that occurs while `Tick()` is running will coalesce into a new
  signal, causing an *extra* `Tick()` after the current one finishes.
- The spec predicts a lower bound on `Tick()` invocations per work item. The
  real system may invoke `Tick()` more often (but never fewer times).
- The extra `Tick()` calls are benign because `Tick()` is **idempotent**: it
  queries ALL pending work from the database, so re-processing is a no-op.

**Why the verified properties still hold:**

- **Safety (`NoDuplicateProcessing`)**: The spec verifies that no item is
  marked DONE without being processed. In the real system, this is guaranteed
  by two mechanisms: (1) the `Serve()` loop is single-threaded — only one
  `Tick()` runs at a time per service instance, preventing overlapping
  processing of the same item; (2) database-level row locking
  (`lockApplication` with `FOR NO KEY UPDATE`) serializes concurrent writes
  from different instances. These mechanisms are independent of processing
  atomicity.
- **Liveness (`EventualProcessing`)**: The spec verifies that the poll timer
  eventually processes all pending work. Since the real system fires the poll
  timer at least as often as the spec's `SyncInterval`, and `Tick()` queries
  all pending work, liveness holds a fortiori.
- **Non-atomic processing + crash:** A worker crash during `Tick()` can leave
  a batch partially processed (some items DONE, others still PENDING). The
  spec does not model this intermediate state, but neither safety nor liveness
  is affected: safety is per-item (each database update is independent), and
  liveness is guaranteed by restart + immediate sync (`WorkerRestart` sets the
  clock to `SyncInterval`, triggering an immediate `SyncWakeup` that re-queries
  all pending items).
- **Coalesce buffer persistence:** The buffer-1 channel in `Coalesce()`
  guarantees that if any notification arrives during `Tick()`, at least one
  signal remains buffered for the next `Serve()` select iteration. This is the
  mechanism that prevents the non-atomic gap from losing events. The spec
  models this atomically (`eventChannel' = {}`) and cannot distinguish "signal
  buffered during processing" from "signal arrived after processing."

**What the spec does NOT verify:**

- The exact number of `Tick()` calls per work item (the real system may invoke
  `Tick()` additional times for the same net effect).
- The interaction between `Coalesce()` buffering and `Serve()` scheduling.
- The timing of event arrival relative to `Tick()` execution boundaries.
- Crash-during-processing effects on snapshot completeness (relevant for PRT
  dispute resolution, but outside the event system's scope).

These are performance characteristics, not correctness properties. The spec
verifies that the system is *correct* (no work loss, no duplicates, eventual
completion), not that it is *efficient* (minimal redundant ticks).

### Reschedule Signal: Level-Triggered vs. Edge-Triggered

The Go implementation's reschedule mechanism is **edge-triggered**: `SignalReschedule()`
deposits one signal in a buffer-1 channel during `Tick()`. The signal is consumed
when the `Serve()` select fires on `rescheduleChan()`. The channel can fire even if
no pending work remains (it was pending when the signal was deposited, but completed
by the time the next `Tick()` runs). The idempotent `Tick()` handles this gracefully.

The TLA+ `RescheduleWakeup(w)` is **level-triggered**: its precondition is the
existence of pending work at the moment of wakeup (`\E i : db[i] = "PENDING"`),
not the presence of a buffered signal. This means the spec allows `RescheduleWakeup`
to fire whenever pending work exists, while the Go code can only fire when a signal
was previously deposited. Conversely, the Go code can fire when no work remains
(stale signal), while the spec cannot.

This is a safe over-approximation for both safety and liveness:
- **Safety**: The spec allows a superset of the Go behaviors, so safety properties
  verified in the spec also hold in reality.
- **Liveness**: The spec's `RescheduleWakeup` is not needed for liveness —
  `SyncWakeup` (SF) provides the guarantee regardless.

## Compositional Independence

The HybridEvents spec models the generic wake-up mechanism. It does not model
what `Tick()` does — that is specified by consumer-specific specs (e.g.,
`DrainProtocol`). The two specs are compositionally independent because
`Tick()` is idempotent and re-queries all pending work from the database.

Events affect only *when* a tick fires, never *what* it discovers. The drain
protocol's correctness depends only on ticks eventually happening (SF fairness),
not on how they are triggered. See `spec/drain-protocol/README.md` for the
drain protocol's corresponding note.
